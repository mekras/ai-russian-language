# Проект

Проект публичный. Репозиторий содержит навыки, которые помогают агентам ИИ
правильно применять русский язык в разных задачах.

Проект использует `ai-dev-team`.

## Концепция

Концепция проекта находится в [README.md](README.md). Перед предметной работой
прочитай её и перед передачей результата проверь, что он ей не противоречит.
Граф влияния находится в [project-impact.json](project-impact.json).

## Входной протокол

Перед ответом, вопросом, исполнением или передачей работы по каждому элементу
корневого входа открой `.agents/skills/ait-routing/SKILL.md`. Если этот путь
недоступен, используй `.claude/skills/ait-routing/SKILL.md`. Следуй открытому
навыку: выбери режим и первым сообщением покажи маршрут со строками «Режим
менеджера», «Причина» и «Маршрут». Если оба файла отсутствуют, остановись и
сообщи о блокере.

## Русский язык

Используй навык [ru-lang](.apm/skills/ru-lang).

`ru-lang: основной, технический, строгий, разработка`

## Корпус знаний проекта

Проект использует корпус знаний в `knowledge/`.

Собственные файлы проекта никогда не включаются в корпус, в том числе
проектные решения из `docs/DR/`. Рабочие разговоры с агентом также исключены.
Запрет распространяется на фрагменты, пересказы и производные утверждения из
этих материалов. Внешние источники допускаются только по решению владельца.
Политика записана в `knowledge/corpus.yml.source_admission`, разрешения на допуск
источников — вне корпуса, в `.ai-dev-team/source-admissions/`.

Перед включением материала проверяй допуск командой:

```bash
python3 .agents/skills/kc-inventory/scripts/validate-corpus-layout.py knowledge --project-root . --admission-only
```

Перед значимыми изменениями в правилах, документации, требованиях, архитектуре
или пользовательских сценариях проверяй, есть ли в корпусе релевантные
источники, утверждения, отчёты влияния или открытые вопросы.

Используй корпус знаний как проверяемое основание для разработки проекта:

- сначала опирайся на источники, утверждения и ограничения из корпуса;
- профильные навыки перед содержательной работой проверяют корпус знаний
  проекта и не заменяют его встроенными справочниками;
- не выдавай выводы из корпуса за принятое решение, если требуется решение
  владельца проекта;
- если корпус противоречит задаче пользователя или текущим файлам проекта,
  явно зафиксируй противоречие;
- если работа меняет смысловые сведения проекта, проверь, нужно ли обновить
  корпус знаний или выполнить анализ влияния;
- если источник нельзя копировать, он слишком большой, часто меняется или
  доступен через права проекта, предложи индексировать его, получать точечно
  или обращаться к первоисточнику вместо хранения полной копии;
- если корпус неполон или структурно повреждён, сообщи об этом как об
  ограничении и не имитируй его проверку.

Для проверки состояния корпуса используй `kc-validation`. Для движения данных
от источников к изменениям проекта используй `kc-pipeline` и соседние навыки
корпуса знаний.

## Журнал изменений

При изменениях проекта проверяй необходимость обновления `CHANGELOG.md`
через `ait-changelog`.

## Проектные решения

Все значимые долгоживущие решения проекта записывай в `docs/DR/` через
`ait-decisions`. Сравнивай варианты сначала по надёжности работы правил, затем
по экономии контекста. Если эти факторы не дают явного выбора, запроси решение
владельца проекта. Не выполняй решение до его принятия владельцем.

## Подагенты

Не используй подагентов при работе с этим проектом. Выполняй задачи основным
агентом без делегирования через `spawn_agent`, fan-out или отдельные процессы
Codex, включая `tools/codex-model-subagent` и `tools/codex-spark-subagent`.
Наличие файлов `.codex/agents/*.toml` и инструментов запуска не разрешает их
использование. Настройка Codex в `.codex/config.toml` отключает многоагентный
режим. Возобновление использования подагентов требует нового явного решения
владельца проекта.

## Внесение изменений

- Разрешается вносить изменения только внутри папки проекта.

## Проверки команд

При изменении ввода, справки или сообщений команд проекта заранее определи
обязательные автоматические проверки основного сценария и затронутых ошибок.
Изменение готово только после их успешного выполнения. Пропуск обязательной
проверки оставляет задачу незавершённой.

## Git

- Все изменения, даже чужие, если они не исключены через `.gitignore`, сразу
  добавляй в индекс Git.
- Не делай commit и push без явной просьбы пользователя.

## Сообщения коммитов

Используй схему `pro-git`. Пиши сообщения по-русски, начиная заголовок с
прописной буквы и краткого страдательного причастия, согласованного с названием
результата.

## Выпуск новой версии

- Перед выпуском новой версии тесты надо выполнять только если тесты для
  сделанных изменений не выполнялись.
